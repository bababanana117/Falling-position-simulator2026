新技術スタック提案
====================

.. note::

   これは、リニューアル前(jQuery/Leaflet版の静的サイト)の時点で書かれた
   検討資料である。ここで比較している案Bの方向性(Pythonバックエンド+
   React/TypeScriptフロントエンド)が、コミット ``94887cb`` の全面書き換え
   でおおむね実現されている。現在の構成は :doc:`architecture` を参照の
   こと。以下は当時の検討内容をそのまま残したものであり、現在の実装と
   一致しない記述が含まれる。

達成したいこと
----------------

現行実装(:doc:`architecture` 〜 :doc:`known_issues`)を踏まえ、
リニューアルで実現したい要件を整理する:

1. **多数パラメータの入力** — 発射地点・日時・上昇率・バースト高度・
   降下率に加え、ペイロード質量・バルーン種別・ガス種別など、
   :doc:`ascent_calculator` 相当の設計変数も含めて一括で扱う
2. **大規模モンテカルロ試行** — 数百〜数千回規模の試行を現実的な時間で
   実行し、着地分布を確率的に(信頼楕円・ヒストグラム等を含め)提示する
3. **多様な可視化** — 着地分布ヒートマップ、高度プロファイル、
   感度分析(どのパラメータが着地距離に効くか)などのグラフ群
4. **最適化提案** — 「この時期ならどこから打ち上げるべきか」
   「ヘリウム量(≒上昇率/バースト高度)はどれくらいが良いか」を
   自動算出する
5. **(必要なら)自前の大気・軌道シミュレーション** — 外部Tawhiri APIへの
   完全依存から脱却し、風・大気モデルを内製することも視野に入れる

比較の軸
----------

各案を「ホスティング制約」「外部API(Tawhiri)依存」の2軸を含めて評価する。

.. list-table::
   :header-rows: 1
   :widths: 18 27 27 28

   * -
     - 案A: 静的サイト継続
     - 案B: Pythonバックエンド導入
     - 案C: ハイブリッド(段階移行)
   * - ホスティング
     - GitHub Pages(無料・現状維持)
     - Fly.io / Render / 自前サーバー等(有料 or 要運用)
     - 短期はGitHub Pages、中長期で計算部分のみサーバーレス関数等に分離
   * - Tawhiri依存
     - 継続(WASM移植すれば軽減余地はあるが実質困難)
     - 自前化可能(GFS/Open-Meteo等から風データ取得し独自積分)
     - 短期は継続、中長期で計算負荷の高い部分から自前化
   * - モンテカルロ規模
     - 数百件が実用上限(Web Worker並列化前提)
     - 数千〜数万件も現実的(サーバーCPU/マルチプロセスで並列実行)
     - 短期は数百件、中長期でサーバー移管後に拡大
   * - 最適化機能
     - クライアントJSでの簡易グリッドサーチ程度
     - scipy.optimize / Optuna等によるまともな最適化が可能
     - 短期は非対応、中長期でサーバー側に実装
   * - 移行リスク・コスト
     - 低い(現行踏襲)
     - 高い(サーバー運用・認証・コスト管理が新規発生)
     - 中程度(段階的なので都度検証できるが、一時的に二重管理になる)

案A: 静的サイト継続 + クライアントサイド計算強化
---------------------------------------------------

**方針**: GitHub Pagesの無料ホスティングと運用の単純さを維持しつつ、
フロントエンドの技術だけを刷新する。

.. list-table::
   :header-rows: 1

   * - 領域
     - 技術候補
   * - 言語/ビルド
     - TypeScript + Vite(ビルドレス脱却、型安全性確保)
   * - フレームワーク
     - React または Svelte(現行のjQuery直接DOM操作から状態管理ベースへ)
   * - 可視化
     - Plotly.js(散布図・ヒストグラム・等高線) + deck.gl または
       Leaflet継続(地図描画)
   * - モンテカルロ実行
     - Web Worker(複数)でTawhiriリクエストを並列化。もしくは
       Rust/C++で書いた軌道積分ロジックをWASMにコンパイルしブラウザ内で
       完結させる(Tawhiri依存を部分的に解消)
   * - 最適化
     - クライアント側で軽量なグリッドサーチ/山登り法程度に限定

**長所**: 運用コストゼロ、現行のデプロイフロー(GitHub Actions→Pages)を
そのまま使える。**短所**: ブラウザのCPU/メモリ制約により大規模モンテカルロ
(数千件)や本格的な最適化アルゴリズム、独自大気シミュレーションの実装は
非現実的。

案B: Pythonバックエンド導入 + モダンフロントエンド
------------------------------------------------------

**方針**: 計算をサーバー側に持たせ、要件1〜5を正面から満たす。

.. list-table::
   :header-rows: 1

   * - 領域
     - 技術候補
   * - バックエンド
     - FastAPI(Python)。非同期I/OでTawhiri/気象API呼び出しと自前計算を両立
   * - 数値計算
     - NumPy/SciPyでルンゲクッタ法等による軌道積分。
       ``multiprocessing`` / ``joblib`` / Rayでモンテカルロを並列実行
   * - 気象データ
     - GFS(NOAA NOMADS)やOpen-Meteo等のオープンデータを直接取得し、
       独自の風・大気モデルで積分(Tawhiri依存を解消する場合)。
       移行初期はTawhiriへのフォールバックも可能
   * - 最適化
     - ``scipy.optimize`` (勾配法・グリッドサーチ)や
       Optuna (ベイズ最適化)で「着地誤差最小化」「回収可能性最大化」等を
       目的関数に発射条件(地点・時刻・ヘリウム量)を探索
   * - フロントエンド
     - React + TypeScript、可視化はPlotly.js/deck.gl、地図はLeaflet継続
   * - ホスティング
     - フロントは引き続き静的配信可、バックエンドはFly.io / Render /
       Cloud Run等

**長所**: モンテカルロ規模・最適化・自前大気モデルいずれも実用レベルで
実現可能。将来的な機能拡張(実測データとの比較、リアルタイム更新等)にも
強い。**短所**: サーバー運用(コスト・可用性・セキュリティ)が新たに
発生し、現行の「無料・ゼロ運用」という利点を手放すことになる。

案C: ハイブリッド(段階移行)
--------------------------------

**方針**: 移行リスクを抑えるため、案A→案Bへ段階的に寄せる。

1. **短期**: 案Aの延長でフロントエンドをTypeScript化し、可視化(Plotly.js)
   とモンテカルロのWeb Worker並列化のみ先行導入。Tawhiri依存は維持
2. **中長期**: 計算負荷が高い部分(大規模モンテカルロ、最適化、自前大気
   シミュレーション)だけをサーバーレス関数(例: AWS Lambda / Cloudflare
   Workers、あるいは軽量なFastAPIサーバー)に切り出し、フロントは
   静的配信のまま維持。バックエンドが必要なときだけ呼び出す構成

**長所**: 各段階で動くものを検証しながら進められ、途中で止めても
その時点の改善が無駄にならない。**短所**: 移行期間中はTawhiri直叩き
経路とバックエンド経由経路が併存し、一時的にコードパスが複雑になる。

想定ライブラリまとめ
------------------------

.. list-table::
   :header-rows: 1

   * - 用途
     - 候補
   * - モンテカルロ並列実行(サーバー)
     - Python: ``multiprocessing`` / ``joblib`` / Ray
   * - 数値積分
     - SciPy(``solve_ivp`` 等のODEソルバー)
   * - 最適化
     - ``scipy.optimize``、Optuna(ベイズ最適化)、DEAP(遺伝的アルゴリズム)
   * - 可視化(散布図/ヒートマップ/ヒストグラム)
     - Plotly.js(フロント)、Plotly/Matplotlib(サーバー側で事前生成する
       場合)
   * - 地図・3D軌道表示
     - Leaflet(継続)、deck.gl(大量点群の高速描画)
   * - 気象データ取得
     - Open-Meteo API、NOAA GFS(NOMADS)、herbie-data(Python用GFS取得
       ライブラリ)
