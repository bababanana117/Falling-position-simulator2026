現状の限界・既知の課題
========================

現在のコードを読んで確認した、動作上の制約や既知の制限をまとめる。
いずれもコード読解に基づく記述であり、該当する箇所のファイルを挙げている。

モンテカルロは風そのものを揺らさない
----------------------------------------

予報窓内のモンテカルロ(:doc:`monte_carlo`)は、上昇速度・破裂高度・
降下速度の3パラメータだけを乱数で揺らし、それぞれの組み合わせについて
個別にTawhiriへリクエストする(``frontend/src/mc/sampling.ts``)。
各リクエストはTawhiri側では同じGFS風データを参照するため、風速・風向
そのものの不確実性(予報誤差、アンサンブルの広がり等)は表現されない。
統計モード(:doc:`climatology`)はこの逆で、風の統計的な散らばりから
落下点を求めるが、発射条件(上昇速度等)は揺らがない。

Open-Meteo Elevation APIの1分あたりの制限
----------------------------------------------

着地点の安全判定で使う標高取得(``frontend/src/safety/elevation.ts``)は、
Open-Meteo Elevation APIを100点ずつのバッチで呼び出す。このAPIには
1分あたりのリクエスト数制限があり、モンテカルロの標本数や最適化のセル数
が多いと429(レート制限)が返ることがある。429のときは61秒待って同じ
バッチを1回だけ再試行し、それでも失敗した場合はその点の標高を
``null``\ (「標高不明」)として扱う。このため、UI側のモンテカルロ標本数の
上限は500件に制限されている(``MC_MAX_SAMPLES``、バックエンドの統計
モード自体は最大2000件まで受け付ける)。

地図が入力した座標へパンしない
----------------------------------

緯度経度を数値入力で変更したり、発射地点プリセットを選んだりすると、
発射地点マーカー(``frontend/src/components/map/LaunchMarker.tsx``)の
位置は更新されるが、地図本体の表示範囲は変わらない。``MapView.tsx`` の
``MapContainer`` は ``center``/``zoom`` を初期値(北海道十勝付近、
ズーム9)で固定しており、マーカーの位置に合わせて自動的にパンする処理が
無い。遠方の地点に切り替えた場合、利用者が手動で地図をスクロール・
ズームしないとマーカーが画面外になることがある。

統計モードの着地分布グラフで値が一定・空になる項目がある
--------------------------------------------------------------

統計モードの標本は ``frontend/src/api/climatology.ts`` の
``toSampleFlights()`` で ``Flight`` 型に変換されるが、この変換には
次の2つの制約がある。

- 各標本の ``perturbed.burstAltitude`` は、リクエストした破裂高度
  (``req.burst_altitude``)がそのまま全標本に入る(統計モードは風の
  ばらつきで散らばりを作るため、破裂高度自体は揺らがない)。そのため、
  着地分布グラフ(``LandingScatter.tsx``)の色分け(バースト高度の
  カラーバー)は統計モードでは実質的に一色になり、情報を持たない
- 各標本の ``ascent`` / ``descent`` は空配列になる(着地点の緯度経度と
  飛行時間のみを持つ)。そのため、高度プロファイルグラフ
  (``AltitudeProfile.tsx``)のモンテカルロ標本の折れ線は統計モードでは
  何も描画されない。描画されるのは平均の軌道(中心予測)の1本だけである

統計モードが対応していない機能
------------------------------------

統計モードは単発予測とモンテカルロのみに対応する。時系列予測
(``runHourly``)・発射条件最適化・感度分析は予報窓内の時刻のみを前提に
しており、予報窓を超えた時刻は(時系列予測の場合)静かにスキップされる
だけで、統計モードの計算には切り替わらない。

バックエンドに未使用の実装が残っている
--------------------------------------------

``backend/bfps/core/`` には自前の大気・軌道積分・モンテカルロ・最適化の
実装があり、``bfps/api/routes_simulate.py`` / ``routes_optimize.py`` から
``POST /api/simulate`` / ``POST /api/montecarlo`` / ``POST /api/optimize``
として公開されている。しかし、現在のフロントエンドはこれらを一切呼び出し
ておらず、呼び出しているのは統計モードの
``POST /api/climatology/predict`` のみである(:doc:`architecture`)。
